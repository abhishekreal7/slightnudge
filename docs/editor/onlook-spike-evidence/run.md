## 7. First three work items for B

**CONFIRMED.** SlightNudge’s imported studio already renders presets for dimensions, layout, fill and typography from `importedStyleOptions`. Its preset list omits border width/color, font style and text decoration even though the engine allowlists them. [S1, S6](#source-index)

1. **Recommendation.** Extend the existing imported-repository controls using the engine’s allowlist. Start with border width, border color, font style and text decoration, which the style API supports and the imported preset list omits. Group them with the existing width, flex, fill and typography controls, and show refused selections and read-only values explicitly. [S6](#source-index)
2. **Recommendation.** Keep one reviewed edit intent tied to the current repository/path/line/column. Invalidate stale previews on selection or variant changes. Use the existing apply and undo responses to refresh the canvas and surface precise refusals.
3. **Recommendation.** Add opacity first as a new capability, then bounded height and directional spacing. Specify each utility’s conflict group, validate it with the target Tailwind setup, and exercise apply/undo before exposing it in the UI.

**Main risk and first test.** A control can appear to affect one rendered element while changing multiple source consumers or an adjacent variant. Start with the lab’s same-line Hero spans. Preview one supported style on the second span, confirm the diff changes exactly its intended class token, apply and undo while preserving an unrelated manual edit, then exercise an external edit between preview and apply. Run the same control against the FAQ `cn`/map row, a shared component and a conditional ancestor. Require explicit, consistent apply and undo semantics for each. **UNVERIFIED.** these are proposed acceptance tests.
